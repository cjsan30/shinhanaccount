# 추가 리팩터링 계획

이 문서는 기능 동작을 바꾸지 않고 유지보수성과 회귀 방어력을 높이기 위한 구조 개선 항목을 기록한다. 각 항목은 기능 변경과 섞지 않고 별도 커밋으로 진행한다.

## P1 — 화면 조정자 축소

현재 `App.tsx`는 앱 상태 연결뿐 아니라 패널별 JSX, 결제 수정·삭제·취소, 정책 관리와 규칙 관리 이벤트를 함께 소유한다.

- 목표: `App.tsx`는 초기화, 최상위 상태, 라우팅만 담당한다.
- 분리 단위: `payments`, `policy`, `rules`, `settings`, `evidence` 기능별 화면과 훅.
- 완료 기준: 패널별 JSX가 기능 폴더로 이동하고, 화면 전환 계약은 `navigation.ts` 한 곳에서 관리된다.
- 안전장치: 분리 전후 사용자 흐름 테스트 결과와 저장 데이터 형식이 같아야 한다.

## P1 — 기간·집계 선택자 단일화

현재 화면 일부가 거래 배열을 직접 필터링하고 도메인 모듈도 별도 집계 함수를 사용한다.

- 목표: 기간 판정, 분류 상태, 취소 상태, 현재일까지의 범위를 순수 선택자 함수로 통일한다.
- 완료 기준: 대시보드, 상세, 결제 목록, 알림 동기화, 위젯 스냅샷이 같은 선택자를 사용한다.
- 금지: 화면 컴포넌트에서 `periodKey` 문자열을 직접 비교하지 않는다.

## P1 — 네이티브 수신과 예산 계산 계약 정리

- Kotlin은 승인 이벤트 수집·대기열 저장·알림 게시를 담당하고, TypeScript는 최종 분류·집계를 담당한다.
- 앱이 닫혀 있을 때 필요한 즉시 경고용 네이티브 계산은 동일한 기간·반올림·임계치 테스트 벡터를 공유한다.
- 자동 분류 규칙이 사용자마다 달라지는 점을 고려해 네이티브 하드코딩 규칙을 장기적으로 제거하고 동기화된 규칙 스냅샷을 사용한다.

## P2 — 저장소와 마이그레이션 계층

- SQLite 쿼리, 도메인 직렬화, 레거시 `localStorage` 이동을 각각 저장소 어댑터와 마이그레이션으로 분리한다.
- 스키마 버전을 명시하고 각 버전의 상향 마이그레이션과 실패 복구 테스트를 둔다.
- UI는 SQLite·Keystore 세부 구현을 직접 알지 않도록 저장소 인터페이스만 사용한다.

## P2 — 증빙 PDF 파이프라인

- 선택 → 순서 지정 → 이미지 정규화 → 압축 → PDF 조립 → MediaStore 저장을 단계별 모듈로 분리한다.
- 압축 결과 재사용과 메모리 상한 제어는 GitHub 이슈에서 별도로 추적하며, 승인 전에는 구현하지 않는다.
- 향후 WorkManager 전환 시 UI와 생성 엔진을 재작성하지 않도록 진행률·취소·완료 결과 계약을 먼저 정의한다.

## 진행 원칙

1. 한 커밋에는 한 리팩터링 목적만 포함한다.
2. 공개 데이터 형식과 사용자 화면 동작을 바꾸지 않는다.
3. 각 단계 전후 자동 테스트와 핵심 실기기 체크를 비교한다.
4. 대규모 일괄 이동보다 컴포넌트·선택자·저장소 순으로 작은 단위로 진행한다.
