# README 포트폴리오 검토 및 보완 계획

작성일: 2026-08-24  
목적: 개인 학습 프로젝트 README를 채용 담당자가 이해하기 쉬운 포트폴리오 문서로 보완한다.

## 프로젝트 한 줄 정의

`신청해` 지원사업 참가자가 정해진 지원 항목과 금액 안에서 지원금을 사용하도록 돕는 Android 앱이다. 카드 결제 알림과 카드사 거래내역을 바탕으로 카테고리별 사용량·가용 금액을 보여주고, 월별 사용 보고서에 필요한 증빙 파일 준비를 지원한다.

## 검토 기준

- 기능 목록보다 실제 문제와 사용자 흐름을 먼저 보여준다.
- AI를 사용했더라도 요구사항 정의, 예외 처리 기준, 검증 책임은 프로젝트 작성자가 맡았음을 판단 근거로 드러낸다.
- 구현 완료 기능과 계획·보류 기능을 명확히 나눈다.
- 실제 거래 정보, 카드 정보, 계정 정보, 서명 정보는 문서와 이미지에서 제외한다.

## 1. 실제 동작 증거

### 질문

“정말 동작하는 앱인가요?”

### 현재 아쉬운 점

README에 기능과 기술 스택은 있으나, 첫 화면에서 실제 앱의 동작과 완성도를 판단할 수 있는 시각 자료가 없다.

### 보완 방향

README 상단의 프로젝트 소개 뒤에 다음 3장의 앱 화면 이미지를 넣는다.

1. 지원금 관리 대시보드: 총 잔액, 정주비, 학습공간비를 한 화면에 보여주는 화면
2. 결제 내역 확인: 상호명·분류·금액을 확인하고 미정 지출을 처리하는 화면
3. 증빙 PDF 또는 데이터 관리: 보고서 준비 흐름을 보여주는 화면

이미지에는 실제 카드번호, 결제처, 결제금액, 계좌 정보가 포함되지 않은 테스트 데이터만 사용한다.

### 현재 답변

주요 기능에 이미지 3장을 삽입한다.

### README 반영 여부

이미지 준비 후 반영.

## 3. AI 활용과 작성자 판단

### 질문

“AI를 활용했다면, 본인이 내린 핵심 판단은 무엇인가요?”

### 현재 아쉬운 점

기능 범위가 넓어 AI가 구현을 주도하고 작성자의 역할은 불분명했다고 해석될 수 있다.

### 보완 방향

대외 README에는 AI 사용 사실을 과도하게 설명하지 않는다. 대신 실제 요구사항·정책·예외 처리 기준을 작성자가 정의한 사례를 3개만 선별해 설계 판단으로 보여준다.

### 현재 답변

기획 단계와 개발 중 고민했던 결정 사항을 다시 떠올려야 한다. 우선 로컬 문서에서만 후보를 정리한다.

### 로컬 후보

- 지원금 정책 확정 전 결제는 예산에 자동 반영하지 않고 미정 지출로만 다룬다.
- 자동 분류는 편의 기능이며, 확신이 없으면 미정으로 두고 사용자가 최종 확정한다.
- 카드 내역의 마스킹 식별값 앞 3자리가 중복되면 가져오기를 중단한다.
- 결제 알림은 카드사 문자만이 아니라 메시지 앱·카드 앱 알림 환경을 고려한다.
- 증빙 PDF는 자동 판정 대신 사용자가 자료와 순서를 직접 확인하는 흐름을 우선한다.

### README 반영 여부

후보 중 실제로 가장 설득력 있는 3개를 확정한 후 반영.

## 4. 결제 알림 인식 방식

### 질문

“왜 SMS 권한 대신 알림 접근을 사용했으며, 어떤 환경을 지원하나요?”

### 현재 아쉬운 점

현재 설명은 알림 접근을 사용한다는 결과만 있고, 사용자의 실제 카드 알림 환경과 권한 선택의 이유가 드러나지 않는다.

### 보완 방향

Samsung Messages 환경에서 카드 승인 메시지가 일반 SMS 수신으로 처리되지 않는 경우를 확인했고, 카드 앱 설치를 전제로 알림 접근을 이용했다는 배경을 간단히 설명한다. 카드 앱·메시지 앱 알림이 함께 오는 경우에는 중복 승인 방지 기준이 필요하다는 점도 함께 적는다.

### 현재 답변

삼성 메시지 환경에서는 결제 카드 승인 메시지를 일반 SMS 수신으로 안정적으로 인식할 수 없었다. 따라서 앱 알림을 활용했으며, 사업 참여자가 카드사 앱을 필수로 설치하는 사용 환경을 전제로 했다.

### README 반영 여부

반영 대상. 단, 특정 제조사 동작을 일반화하지 않고 “검증한 사용 환경”으로 표현한다.

## 5. 로컬 저장소 보안 설명

### 질문

“암호화 저장소는 무엇을 보호하며, 한계는 무엇인가요?”

### 현재 아쉬운 점

“기기 내 암호화 저장소”라는 표현만으로는 보호 대상, 적용 지점, 한계를 알기 어렵다.

### 보완 방향

README에는 구현 세부보다 아래 원칙을 명확하게 쓴다.

- 거래내역·정책·분류 규칙은 서버에 전송하지 않고 기기 내부에 보관한다.
- 앱 데이터는 Android 앱 샌드박스에 분리되어 다른 일반 앱이 직접 접근할 수 없다.
- 민감 상태는 앱의 암호화 저장소를 통해 보관하고, 백업 파일은 사용자가 지정한 암호로 보호한다.
- 기기 자체가 탈취·루팅되었거나 사용자가 백업 암호를 잃어버린 상황까지 완전히 보호하지는 않는다.
- 서버 동기화를 제공하지 않으므로 기기 교체·분실에 대비하려면 암호화 백업을 사용해야 한다.

### 현재 답변

위 원칙을 보안 설명의 기본 답안으로 사용한다. 기술 면접에서는 “서버 미사용·로컬 우선”이 개인정보 전송을 줄이는 선택이었으며, 완전한 위협 모델 해결책이 아님을 함께 설명한다.

### README 반영 여부

반영 대상. 과장된 보안 표현은 피한다.

## 6. OCR의 역할과 실패 처리

### 질문

“OCR 결과를 어디까지 신뢰하나요?”

### 현재 아쉬운 점

OCR 기능이 자동 확정처럼 보이면 정확도와 예외 처리에 대한 의문이 생긴다.

### 보완 방향

OCR을 자동 입력 도우미로 한정하고, 정책 확정은 항상 사용자가 검토·수정한 뒤 수행한다는 흐름을 설명한다.

### 현재 답변

빠른 구현과 입력 편의를 위해 초안을 구성할 때만 OCR을 사용한다. 사용자가 직접 검토하고 확정하는 흐름을 따른다.

### README 반영 문안 초안

> 계획표 OCR은 입력 초안을 만드는 보조 기능입니다. 인식 결과가 비정상적이거나 사용자가 수정이 필요하다고 판단하면 동일한 정책 표에서 직접 금액을 입력한 뒤 확정합니다.

### README 반영 여부

반영 대상.

## 7. 테스트 범위와 한계

### 질문

“무엇을 자동으로 테스트했고, 무엇을 실기기로 확인했나요?”

### 현재 아쉬운 점

“Android 통합 검증”이라는 표현만으로는 테스트의 종류와 재현 범위를 알기 어렵다. 특히 카드사 알림·파일 선택·위젯은 사용 환경 의존성이 있다.

### 보완 방향

기능 단위로 자동 테스트와 수동 검증을 분리해 나열한다. 각 항목은 인사담당자도 이해할 수 있는 사용자 결과 중심 문장으로 쓴다.

### 현재 답변 및 정리 초안

#### 자동 테스트

- 예산: 항목별 사용액·잔액·경고 비율 계산이 정확한지 확인
- 정책: 정책 확정 전후 지출 처리와 정책 변경 시 미정 지출 처리 확인
- 결제 중복: 카드 앱 알림과 메시지 앱 알림이 같은 승인을 가리킬 때 한 건만 저장되는지 확인
- 자동 분류: 상호명 포함 규칙, 미정 처리, 수동 분류 후 예산 반영 확인
- 카드 파일 가져오기: 마스킹 카드 식별값이 충돌하면 가져오기를 중단하는지 확인
- 백업·복원: 암호화 백업 파일을 생성하고 복원했을 때 정책·지출·규칙이 유지되는지 확인
- 화면 흐름: 온보딩, 거래내역 등록, 미정 지출, 경고 설정, 데이터 관리 화면의 주요 조작 확인

#### Android·실기기 검증

- 알림 접근 권한을 허용한 뒤 승인 알림을 감지하고 앱 내 지출로 반영하는지 확인
- 앱이 백그라운드에 있을 때도 알림을 받고, 앱을 열었을 때 대기 내역을 반영하는지 확인
- 홈 화면 위젯이 예산 사용량을 표시하고 앱의 지출 변경 뒤 갱신되는지 확인
- Android 파일 선택기로 엑셀·PDF·이미지를 선택하고, 생성한 백업·PDF를 기기에 저장하는지 확인
- 앱을 강제 종료한 뒤 복구 안내와 거래내역 가져오기 흐름이 사용자에게 보이는지 확인

#### 현재 한계

- 실제 카드사·메시지 앱의 알림 형식은 기기·앱 버전에 따라 달라질 수 있어, 사전체험판 사용 환경에서 추가 검증이 필요하다.
- 취소 승인 SMS 자동 매칭은 후속 구현 항목이다.
- 대용량 증빙 PDF는 현재 진행 상황을 표시하지만 백그라운드 작업으로 전환하지 않았다.

### README 반영 여부

반영 대상. 실제 테스트 통과 수와 최근 실행 날짜는 릴리스 직전에 업데이트한다.

## 8. React·Capacitor·Android Native 역할 분담

### 질문

“왜 React 기반 앱에 Kotlin·Java 코드가 함께 있나요?”

### 현재 아쉬운 점

기술 스택 표는 있지만 역할 경계가 보이지 않아, 각 기술이 어떤 문제를 해결하는지 알기 어렵다.

### 보완 방향

README에 역할 분담을 짧게 추가한다.

| 계층 | 담당 역할 |
| --- | --- |
| React + TypeScript | 대시보드, 온보딩, 정책 입력, 결제·증빙 관리 화면과 도메인 계산 |
| Capacitor | 웹 UI와 Android 네이티브 기능을 연결하는 컨테이너·플러그인 브리지 |
| Kotlin / Java | 알림 접근, 로컬 파일 저장, 앱 상태 확인, 홈 화면 위젯처럼 Android API가 필요한 기능 |
| SQLite | 정책·지출·분류 규칙·설정의 로컬 지속성 |

### 현재 답변

웹 UI는 React로 빠르게 구현하고, Android 운영체제 기능이 필요한 부분은 Capacitor 플러그인을 거쳐 Kotlin·Java로 구현했다.

### README 반영 여부

반영 대상.

## README 보완 우선순위

### P0: 이미지와 첫인상

1. 실제 앱 화면 3장을 프로젝트 소개 아래에 넣는다.
2. 각 이미지에는 한 줄 설명을 붙인다.
3. 테스트 데이터만 사용하고, 실제 결제·계좌·카드 정보는 노출하지 않는다.

### P1: 문제·판단·검증의 설득력

1. 대상 사용자와 문제 정의를 신청해 지원사업 흐름에 맞춰 구체화한다.
2. 작성자가 내린 설계 판단 3개를 선정해 이유·대안을 함께 적는다.
3. OCR은 초안 생성용이며 사용자가 확정한다는 원칙을 명시한다.
4. 알림 접근 방식을 택한 배경과 중복 방지 원칙을 간단히 적는다.
5. 자동 테스트와 실기기 검증을 분리해 기능 중심으로 나열한다.

### P2: 기술적 깊이와 유지보수성

1. React·Capacitor·Android Native 역할 분담 표를 추가한다.
2. 로컬 저장·암호화·백업의 보호 범위와 한계를 과장 없이 설명한다.
3. 미구현·보류 기능을 명확히 표시한다.

## 비공개 테스트 및 스토어 이미지 활용 기준

### 현재 비공개 테스트 관련 이미지

비공개 테스트 진행 화면이나 Play Console 화면은 README의 대표 이미지로 쓰지 않는다. 사용자 가치보다 배포 과정이 앞에 보여 프로젝트의 제품 완성도를 낮춰 보일 수 있기 때문이다.

다만 아래 용도로는 활용할 수 있다.

- README 하단의 `배포·검증` 섹션에서 “Google Play 비공개 테스트 진행” 사실을 보여주는 보조 이미지 1장
- 기술 블로그나 포트폴리오 문서에서 배포 파이프라인을 설명하는 증거 자료
- 개인 정보·테스터 이메일·앱 식별자·검토 상태가 보이지 않도록 편집한 이미지

### 향후 프로덕션 출시 후

실제 스토어 등록이 완료되면 README 대표 이미지는 Play 스토어 이미지보다 앱 내부 화면을 우선한다. 스토어 링크와 배지는 소개 문단 또는 하단에 추가한다.

- 대표 이미지: 앱 대시보드, 결제 내역, 증빙 PDF 준비 화면
- 보조 링크: Play 스토어 설치 링크, 비공개 테스트 또는 출시 상태
- 스토어 스크린샷: 앱 내부 이미지와 중복되지 않는 경우에만 사용

### 이미지 파일 운영 원칙

- `store-assets/`에는 스토어 제출용 원본을 보관한다.
- README용 이미지는 `docs/images/` 또는 `assets/readme/`처럼 별도 경로로 관리한다.
- README에는 개인정보가 제거된 고정 테스트 데이터 이미지만 커밋한다.
